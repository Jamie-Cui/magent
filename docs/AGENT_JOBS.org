#+title: Child-Agent Jobs
#+magent_lang: en
#+magent_alt_url: /AGENT_JOBS.zh.html
#+options: toc:nil num:nil

Magent uses durable child-agent jobs for collaborative agent work. This replaces the old one-shot ~delegate~ tool with a small lifecycle that the root agent can coordinate explicitly.

* Tool Surface

The public child-agent tool surface is:

| Tool | Purpose |
|---+---|
| ~spawn_agent~ | Start a child-agent job and return a stable job id. |
| ~send_agent_message~ | Send follow-up input to an existing child job. |
| ~wait_agent~ | Wait for one or more jobs and return status/result data. |
| ~list_agents~ | List child jobs for the current parent session. |
| ~close_agent~ | Close a job and abort its live request when present. |

These tools share the ~agent~ permission key. The parent uses the same job ID
with either executor. A Codex job also stores a thread ID internally for follow-ups.

* Data Model

~magent-agent-job.el~ defines ~magent-agent-job~, the durable record for a child job. Each job stores:

- ~id~
- ~parent-session-id~
- ~agent-name~
- ~task-name~
- ~status~
- ~prompt~
- ~created-at~
- ~updated-at~
- ~transcript~
- ~result~
- ~error~
- ~metadata~

Valid statuses are ~queued~, ~running~, ~waiting~, ~completed~, ~failed~, ~closed~, and ~cancelled~.

The parent session stores these records in the ~agent-jobs~ field of its
~<id>.json~ header. The runtime registry ~magent-agent-job--runtimes~ holds
live execution state keyed by job ID.

~magent-agent-job.el~ also owns status observers. ~wait_agent~ subscribes to
those transitions and uses one deadline timer; it does not poll. Child
transitions schedule parent-session persistence through the session's deferred
save queue, so tool callbacks do not synchronously rewrite session JSON.

* Runtime Flow

1. ~spawn_agent~ creates a ~magent-agent-job~ in the parent session.
2. A Magent child starts the Magent-owned loop. A Codex child starts a Codex ACP
   turn through ~magent-codex.el~. Both return a cancellation function to the
   shared job lifecycle.
3. The child runs with summary-only UI so it does not write its full transcript into the parent conversation body.
4. Completion, failure, and close transitions notify wait observers and update
   the durable job record.
5. Tool results return model-visible JSON summaries to the root agent.

A successful ~spawn_agent~ result includes a machine-readable ~next_action~
that calls ~wait_agent~ with the returned job id. It deliberately omits a
timeout so host policy remains authoritative. When ~wait_agent~ omits its
timeout, it uses a positive ~magent-request-timeout~ or a finite 300-second
fallback. Timing out one wait does not cancel or close the child job.

* Inheritance

Children using the default ~magent~ executor run through ~gptel-request~ and
receive the following context from the parent request.

- project root and session scope
- the parent's model route, unless the child profile specifies its own
- temperature, top-p, reasoning effort, and thinking mode when sharing the parent route
- active skill names and capability context
- effective permission profile bounded by the parent and child agent
- request depth for recursive spawn guards

~magent-child-agent-max-depth~ controls recursive spawning. The default allows direct children and blocks recursive child spawning.

* UI And Resume

The supported agent-shell frontend renders compact child-agent lifecycle
updates. Full child prompt, metadata, result/error, and transcript state remain
persisted under the parent session's ~agent-jobs~ data.

After reloading the parent session, use ~list_agents~ to find saved jobs and
their results. Set ~include_closed~ to true to include closed or cancelled
jobs. A follow-up to a Magent child requires its live runtime. A Codex child
can reopen its saved thread under the conditions below.

* Model Configuration And Migration

Magent profiles select a model by ID and may name a registered gptel backend.
The session model still takes precedence for the primary agent. A child with
an independent route uses its own sampling options or the target defaults.

Elisp profiles that formerly supplied a gptel backend object or a
~(BACKEND . MODEL)~ pair as ~:model~ must supply the registered backend name as
~:backend~ and the model ID as ~:model~. An object without an explicit model uses
~:backend~ alone. Existing scalar ~model~ fields already describe a model on
the default gptel backend. Saving a profile now writes both names when
specified. Previous saves that discarded backend identity need the intended
backend supplied by the user.

* Codex Job Lifetime

To use the built-in ~codex~ profile, install ~codex-acp.el~, authenticate the
Codex CLI, and set ~magent-codex-enabled~ to ~t~ before Magent initializes.
In a project session, ask the primary agent to give Codex a task. A project
profile in ~.magent/agent/~ can select ~executor: codex~ with ~mode: subagent~
and optionally specify a Codex ~model~ and ~effort~. Omit both to use the
Codex defaults.

Once Codex returns a thread ID, Magent saves it with the project directory,
model selection, effort, and actual model. After a job completes or fails,
~send_agent_message~ with the job ID loads that thread, including after a
parent session reload, provided the original Codex profile is available in the
same project. If Emacs restarts with a job still queued, running, or waiting,
Magent marks it ~cancelled~ when restoring the session. Each turn opens its own
ACP connection. Directory permissions granted for that connection expire when
the turn ends.

Magent forwards each workspace permission request with the options offered by
Codex. Only the matching request receives the decision. Closing the job or
aborting its parent cancels the active turn and removes pending approvals.
Codex uses the workspace tools supplied by ~codex-acp.el~ and its own model
configuration. Magent retains the dispatch permission and task transcript.

* Boundaries

This lifecycle intentionally preserves Magent's Emacs-native workflow:

- live Emacs buffers
- isolated ~emacs_eval~, trusted ~emacs_read~, and explicit ~emacs_eval_live~
- agent-shell UI
- project-scoped sessions
- gptel transport

Codex sandbox, seatbelt, bubblewrap, and shell-isolation parity are out of scope.
